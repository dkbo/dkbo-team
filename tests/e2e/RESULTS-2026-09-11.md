## 發現的問題

### ① 員工第一個動作就被審批擋住（嚴重）

員工 cwd 是 worktree（`.worktrees/login`），但它的 brief 切片在主樹的 `.dkbo/tasks/…/briefs/`。
Claude Code 視為工作區外的讀取，`--permission-mode acceptEdits` **不放行**，於是兩位員工在
「讀自己的切片」這一步就雙雙 `blocked`：

```
 Read(/…/e2e-example/.dkbo/tasks/2026-09-11-login/briefs/backend.md)
 Do you want to proceed?
 ❯ 1. Yes
   2. Yes, allow reading from /…/briefs during this session
   3. No
```

這不是偶發：dkbo 刻意把「程式在 worktree、記憶在主樹」分開，所以**每一位員工、每一次派工**
都會撞到。`PROTOCOL.md` 已經預期 `rm -rf`、`git push` 這類危險指令會停在審批，但沒預期
連讀自己的任務檔都會。

而且**批准一個路徑只會跳出下一個**：backend 批准了 `…/briefs` 之後立刻卡在讀 `.dkbo/PROJECT.md`，
frontend 則卡在 `cat` 這個 shell 指令。實測要把員工推到 auto mode 才動得了。

實際要讓兩位員工動起來所花的人工介入：各 3 到 4 次按鍵審批，最後只能把兩位都切到 **auto mode**
才停止打斷。過程中依序被擋的是：讀切片 → 讀 `PROJECT.md` → `cat` → 寫自己的 `state/*.md` → `node -e`。

後果：「領導閒置、員工自己做」的模型不成立 —— 每開一個員工就要人連按數次鍵。
員工的權限模式若不是 auto，dkbo 的協定（讀切片、寫 state、寫 report、跑測試）一步都走不完。

附帶測到：Claude Code 的 `shift+tab` 循環順序是 **accept edits → plan → auto**。
中途誤切到 plan mode 會讓員工連改 worktree 內自己擁有的檔都要問。

### ② 領導自己也被 Bash 審批擋住

領導以 `--permission-mode acceptEdits` 起動時，`/dkbo-init` 第 1 步的
`bash -c '. .dkbo/lib/common.sh; …; dk_kinds_available'` 就要審批。改選「switch to auto mode」
後才能繼續。`kinds/claude.sh` 的 `kind_args` 送的是 `--permission-mode acceptEdits`，
對照本次實況，該值可能需要重新考慮。

### ③ 首次在新目錄啟動會有「是否信任這個資料夾」詢問

`herdr agent start` 回 `agent_not_ready: blocked during startup`。要先 `pane send-keys down enter`
選「Yes, I trust this folder」才會就緒。任何新的 worktree 路徑都會遇到。

### ④ `dk-task-new` 只在 agent「完全沒有名字」時才改名，否則訊息路由整條靜默失效（嚴重）

`dk-task-new:50-53`：

```bash
current=$(herdr agent get "$HERDR_PANE_ID" | dk_json '.result.agent.name // empty')
if [ -z "$current" ] && ! herdr agent rename "$HERDR_PANE_ID" "leader-$short" >/dev/null; then
```

本次領導是用 `herdr agent start dke2e` 起的、已經有名字 `dke2e`，於是 rename 被跳過。
而 `dk_leader_name()` 固定回 `leader-$DK_SHORT`，所以：

- 員工的 `dk-msg leader` 送不到
- `dk-watch` 的 `[BLOCKED]` / `[TIMEOUT]` 也送不到

**而且完全沒有警告** —— `process.md` 照樣寫 `blocked login-backend`，看起來一切正常。
手動 `herdr agent rename wB:pB leader-login` 之後訊息才通。

判斷：這不是本次起法造成的例外。人自己開的 Claude Code pane 通常沒有 herdr agent 名字，
所以平常會改名成功；但只要領導的 pane 曾被命名過（例如用 `herdr agent rename` 取過名、
或像本次用 `agent start <name>` 起的），整套訊息路由就靜默斷掉。條件應該是
「不等於 `leader-$short` 就改名」，而不是「沒有名字才改名」。

### ⑤ `dk-spawn` 的 `prompt-failed` 是誤判：把「第一輪超過 60 秒」當成「提示沒送到」（嚴重）

`dk-spawn:81`：

```bash
if herdr agent prompt "$agent" "$(dk_first_prompt …)" --wait --timeout 60000 >/dev/null; then
```

但 `herdr agent prompt --wait` 的語意是（`--help` 原文）：

> Wait for the first matching state observed after submission …
> It then matches **idle, done, or blocked** by default

也就是**等這一輪跑完**，不是「提示是否送達」。本次 `login-reviewer-b`（codex）第一輪讀差異包
超過 60 秒仍在 `working`，於是 `--timeout 60000` 逾時、`dk-spawn` 回非零、被記成
`prompt-failed` —— 而實際上它**正常運作中**，最後也正常交出 report。

後果比誤記一行嚴重：
- `dk-spawn` 在這條路上 `exit 1`，`dk-review` 把該 reviewer 標成 `prompt-failed`
- `LEADER.md` 的故障段教領導「`herdr agent read` 看狀態，再 `herdr agent prompt` 重新提示」
  —— 也就是對一個**正在工作的** agent 再送一次同樣的指令。而 claude 會把提示排隊（見下），
  所以那位員工會在做完之後又收到一次一樣的任務。

正確寫法是用 `--until working` 確認「提示被接受且開始跑」，而不是等整輪結束：

```bash
herdr agent prompt "$agent" "…" --wait --until working --timeout 15000
```

`herdr --help` 另註明：非 working 狀態送出後，`--wait` 本來就要求 5000ms 內觀察到
working 或 blocked，否則回 `agent_prompt_stalled` —— 送達與否已經由那一段保證了，
60 秒那個逾時只是多餘且有害。

### ⑥ 權限問題只發生在 claude，codex 不受影響

`kinds/codex.sh` 用 `-a never -s workspace-write`，整趟沒有跳過任何審批，
`login-reviewer-b` 從頭到尾沒被擋。相對地 claude 的 `--permission-mode acceptEdits`
讓 backend、frontend、reviewer-a 三位全部卡住。問題①本質上是 **claude kind 的旗標選擇問題**，
不是 dkbo 的架構問題 —— 但它讓「多模型」在實務上變成「只有 codex 能無人值守」。

## 順帶驗證到的

### 0.2.1 的 dk-watch 重試修正：現場命中

上面 ④ 造成的送不到，剛好是 0.2.1 那條修正的實戰情境。實測：

- 兩則 `[BLOCKED]` 送不到時，標記檔停在 `notified`，**沒有**寫 `delivered`
- `process.md` 的事件行與桌面通知各只發生一次（不重複騷擾）
- 手動改名讓 `leader-login` 存在之後，下一個 tick **自己把兩則都補送達**，標記才補上 `delivered`

舊版（0.2.0 以前）會把這兩則射進虛空、標記照寫，通知永久遺失且無跡可尋。

### `KIND_PROMPT_QUEUES`：claude 是「排隊」不是「丟掉」

第二則 `[BLOCKED]` 在領導正在工作時送達，pane 顯示 `Press up to edit queued messages`。
所以對 `claude`（2.1.268）而言，送給 working agent 的提示會排隊。codex 與 agy 仍未測。
這不改變 0.2.1 修正的必要性（它保證送達，且涵蓋另外兩個 kind），但可以把 claude 那一格
從 `unknown` 改成已知。

### ⑨ `dk-task-close` 不 commit 任務記憶，README 的核心主張沒有被任何一步落實（嚴重）

結案合併完成後，主樹的狀態是：

```
 M .dkbo/tasks/INDEX.md
?? .dkbo/tasks/2026-09-11-login/
```

整個任務目錄 —— `brief.md`、`process.md`（含 7 條 ruling）、每位員工的 state 與 report、
`report.md`、`messages.log`、`waves/*.diff` —— **全部是 untracked**。`INDEX.md` 也只是 modified。

`dk-wave-close` 會在 **worktree 內** commit 那一波的程式碼，但任務記憶住在**主樹**的
`.dkbo/tasks/`，沒有任何腳本碰過它。`grep -n "commit" .dkbo/bin/dk-task-close` 只有一行，
而且是「worktree 有未 commit 變更就拒絕結案」的檢查。

README 寫「所有記憶都是小型 markdown……進 git」，`decisions.md` 也寫「messages.log 與 state 檔
可讀、可 grep、**進 git**，是設計選擇不是過渡方案」。但實際上沒有任何一步把它們放進 git ——
一個 `git clean -fd` 就會抹掉整個任務的歷史與所有裁定理由，而且不會有任何警告。

`dk-task-close` 結案時應該一併 `git add .dkbo/tasks/<t> .dkbo/tasks/INDEX.md .dkbo/decisions.md`
並 commit。

### ⑩ `[FIXED]` 在 leader→dev 的 BUG 路徑上結構性不會出現

RUNBOOK 的驗收條件要求 `messages.log` 有 `BUG`、`FIXED`。實跑結果：`BUG` 4 筆、**`FIXED` 0 筆**。

原因不是誰忘了送。`PROTOCOL.md` 的類型表把 `FIXED` 定義為**員工→員工**（「修好了，請重驗」），
而 reviewer 的 Important 是由**領導**轉成 `[BUG]` 給 dev 的（`BUG | 員工→員工、領導→dev`）。
dev 修好之後要回報給領導，而領導這一側沒有定義對應的回覆類型，所以三位 dev 都回了 `[DONE]`：

```
19:42 login-qa -> leader-login [DONE] 已修AC1恆真斷言問題，改3條具體斷言，npm test全過(8/8)…
19:53 login-frontend -> leader-login [DONE] frontend 波3修 Important 4 完成…
20:02 login-backend -> leader-login [DONE] BUG(null解構)已於波4修好且重驗通過…
```

行為本身合理（回 DONE 讓領導重跑 review-pack），但 RUNBOOK 的驗收條件對不上實際設計。
要嘛 `PROTOCOL.md` 補一條「dev 回應領導轉來的 BUG 用 `[FIXED]`」，要嘛 RUNBOOK 拿掉那個條件。

## 偏離 RUNBOOK 的地方

- RUNBOOK 預期波次是 wave1 `backend+qa`、wave2 `frontend`。領導自己分成 wave1 `backend+frontend`
  平行、wave2 `qa`。這個分法其實更合理（qa 要兩邊都有東西才測得動），不算錯，但 RUNBOOK 第 4、5 步
  （BUG 迴圈與 ESCALATE）原本掛在 wave1 的 qa 身上，要順延到 wave2。
- RUNBOOK 第 5 步預期 qa 的 ESCALATE 會讓領導升關卡②問人。實際上領導**依 brief 自行裁定**了
  （AC2 原文只寫空字串／缺漏，純空白不在範圍），回 `[DECISION]` 給 qa。這符合 `LEADER.md`
  「能依 brief 判定就自己判」，是正確行為，但等於關卡②這趟沒被觸發。
- step 10（逾時與 kind 熔斷）本次跳過：三家 CLI 都登入可用，沒有天然會逾時的 kind，
  硬調 `DK_REVIEW_TIMEOUT_MIN` 去賭 reviewer 跑不完不可重現。留待單獨設計情境。
- `herdr pane read` 預設來源會回舊畫面，要加 `--source recent-unwrapped` 才是當下狀態。
  驅動腳本若照預設讀會誤判。
- `herdr agent wait` 的狀態名要用 `done`（不是只有 `idle`），否則等不到。
- 7 筆 `UNDELIVERED` 中有 6 筆是員工送給「不在本波的交接對象」（qa 排在後面的波）。
  行為正確，但切片可以明示「本波在線成員」以免白送。第 7 筆是 ⑦ 那筆遺失的 codex 審查。
- 雜務檔名由交代內容截斷而來，本次產出 `2026-09-11-readme-md-rea.md`，可讀性不佳（純美觀）。

## 結論

**核心迴圈是可用的，而且比預期好。** 四道機械閘、越界比對、記憶外置、升報與裁定、
整分支評議、結案合併 —— 全部如實運作，領導的行為與兩份規範逐字相符。整分支評議抓出 5 個
逐波審查結構上看不到的真缺陷，這一步證明了自己的價值。

**但有兩件事會擋住實際使用：**

1. **claude kind 的權限模式**（①）：每個新開的 claude agent 都要人按 3–4 次鍵才動得了，
   本次共介入 7 次。「領導閒置、員工自己做」在 `acceptEdits` 下不成立。
2. **多模型審查閘實際生效率是 0**（⑤⑦⑧）：六次審查，codex 一次都沒真正進入裁定 ——
   一次 DONE 遺失、四次 spawn 失敗、一次誤判 prompt-failed。而 `DK_REVIEW_MIN=1`
   讓領導每次都合法地靜默通過。這是 dkbo 最貴的能力，目前等於沒有開。

**建議的處理順序**：⑧（多模型退化，含 ⑤⑦）→ ①（權限模式）→ ⑨（記憶沒進 git）→ ②④ →
⑩ 與其餘文件層。
