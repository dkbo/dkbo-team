## 需求覆蓋

逐條對照 request.md 的六個缺口與人在設計問答裡的裁定：

1. **brief 的 Interfaces 區塊** → brief 的「共用契約」表已表格化並列出 `dk_brief_interfaces`（AC3）。但這個函式本身**沒有對應「有 reader 與測試」的驗收標準**——AC2 明確要求 `dk_brief_constraints()` 要有 reader 與測試，`dk_brief_interfaces()` 卻沒有平行的一條。共用契約表把它列成「波1 擁有、波1 消費」的正式契約，沒有 AC 驗證意味著它可能沒被真的實作或測試就被波2、波3 消費。**缺口，需補一條 AC。**

2. **TDD 骨架** → 人的原話裁定裡明確寫「`dk-wave-close` 驗：兩個小節都在、都有命令列與輸出」（request.md L47）。但 brief 的 AC5 只寫「`## 測試` 分成 `### 紅`/`### 綠`；`dk-wave-close` 缺任一小節即拒絕」——只驗**小節存在**，沒有涵蓋「內容裡要有命令列與輸出」這個人明確講的驗證項。AC6 的「不適用: <理由>」例外有接住，但「非空≠有命令列與輸出」，這條原話的驗證強度被弱化了。**缺口，AC5 需要改寫成可驗證「內容含命令列與輸出模式」，而不是只驗小節標題存在。**

3. **除錯方法論** → AC7、AC8 接住了「獨立方法檔 + 提示指路」（`methods/debugging.md` 存在、`PROTOCOL.md` 的 BUG 列指向它、首輪提示含指路）。但人的原話還有一句具體裁定：「`[FIXED]` 訊息要求附根因一句」（request.md L59）。翻遍 AC1–AC14，**沒有任何一條要求 `[FIXED]` 訊息格式要含根因**，波次表 Task 6–8 的描述（紅綠小節、gate b、debugging.md、首輪提示）裡也沒提到這件事。**缺口，需要補一條 AC（或明確併入既有 AC）來驗證 FIXED 訊息含根因一句。**

4. **Global Constraints 區塊**（AC1、AC2、AC4）、**Minor 匯總去向**（AC9、AC10）、**修復迴圈中間層**（AC11、AC12、AC13，含「第二輪換腦袋、第三輪升報」對應到「兩輪」的收斂）—— 這三塊需求覆蓋完整，沒有發現缺漏。
5. 「員工要改 `.dkbo/` 這件事怎麼處理」的裁定，brief 的共用契約段落逐字對應（停止條件例外 + ruling 記錄），覆蓋完整。

## 驗收標準可驗證性

- AC1–AC4、AC6、AC8、AC9、AC10、AC12、AC13、AC14：可明確判定過或不過。
- **AC5**：如上，只驗小節存在不驗內容，判定標準比人的原話弱，需要改寫成類似「`### 紅`/`### 綠` 各自非空，且非空內容含 `$` 開頭的指令列與其後至少一行輸出（或 `不適用: <理由>`）」這種可機器判定的形狀。
- **AC7**（`lib/prompt.sh` 的首輪提示含 TDD 順序與 `methods/debugging.md` 指路）：「含 TDD 順序」這個判準模糊——沒有指定要 grep 哪個關鍵字或哪個具體字串，兩個不同做法的實作都可能宣稱自己「含順序」。建議改寫為「首輪提示文字含 `methods/debugging.md` 路徑字串，且含『先寫測試』或等價關鍵字，順序在『紅』之前」這類可 grep 判定的寫法。
- **AC11**（`--handoff` 自動寫 ruling 行，且「用接手版提示」）：「接手版提示」沒有定義判準——與一般首輪提示的差異是什麼字串或欄位？建議明確化為「接手版提示比對照版多帶 HANDOFF 參數且渲染出上一位的 state/report 摘要片段」之類可比對的條件。

## 檔案所有權

只有一個成員 `backend` 全權擁有 `.dkbo/**`、`tests/**`、`CHANGELOG.md`、`README.md`、`README.en.md`，三波都是同一人。沒有重疊問題（只有一人），也沒有找到 AC 要動的檔落在所有權表之外——`lib/`、`bin/`、`methods/`、`skills/` 都在 `.dkbo/**` 之下。獨佔資源欄留空合理（單一成員、無跨波併發）。沒有發現缺漏。

## 波次切法

三波循序、同一人跨波，因此「同波裡有人要等另一人產出」的風險不存在（單人波）。共用契約表的擁有者/消費者方向與波次順序一致：`dk_brief_constraints`、`dk_brief_interfaces`、`{{CONSTRAINTS}}` 都是波1產出、波2或波3消費；`dk_first_prompt` 參數表波2產出、波3消費（新增第9參數不動前8個，有 ESCALATE 護欄）；`## 測試` 紅綠格式波2產出、波3的 report 遵守。順序合理，沒有反向依賴。三波審查欄都填了 `kinds: claude codex`，與難度（L/M/M）相稱。
