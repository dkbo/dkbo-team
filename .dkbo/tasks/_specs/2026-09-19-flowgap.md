# 流程缺口補齊 — 把 superpowers 的六個機制譯進 dkbo

狀態：設計定案，待實作
日期：2026-09-19
來源：與人的對話（brainstorming）
目標版本：0.9.0

## 1. 這是什麼

把 dkbo 與 superpowers 對比後找到的六個缺口，一次補齊。六個缺口照**載體**分成三組，
三組彼此沒有依賴，各自是一波：

| 波 | 組 | 缺口 |
|---|---|---|
| 1 | brief 契約擴充 | 全域約束（Global Constraints）、介面契約（Interfaces） |
| 2 | 品質方法論 | TDD 骨架、systematic-debugging |
| 3 | 審查迴圈 | Minor 匯總去向、修復迴圈的中間層 |

## 2. 為什麼

superpowers 的六個機制在 dkbo 都沒有等價物，而其中四個是 dkbo **結構上做得到、只是沒做**的：
它的強項就是把規則編譯成 exit code，而這四個機制在 superpowers 那側全靠自律（Red Flags 表、
Rationalizations 表）撐著。

- **全域約束**：superpowers 的計畫有 `Global Constraints` 區塊，明文說它是「reviewer 的注意力
  透鏡」，每個 task 的要求隱含包含它。dkbo 的 reviewer 目前只拿到驗收標準與共用契約 —— 版本
  下限、命名規則、平台要求這類橫切約束沒有落腳處，只能塞進「目標 ≤3 行」裡。
- **介面契約**：superpowers 的每個 task 有 `Interfaces: Consumes / Produces`（精確簽名），明文
  理由是「實作者只看得到自己的 task，這個區塊是它認識鄰居的唯一管道」。dkbo 的員工**只讀切片**，
  處境一模一樣，但切片裡只有「共用契約（誰定稿、放哪、變更流程）」這種治理資訊，沒有形狀。
  員工要嘛猜，要嘛發 QUESTION —— 而同一波同一對員工的 QUESTION 上限是兩則。
- **TDD**：dkbo 只要求 report 的 `## 測試` 段非空，沒有一個字規定紅→綠。這是目前最大的方法論空洞。
- **systematic-debugging**：`PROTOCOL.md` 的修復迴圈規定的是**次數上限**（修一次不過就升報），
  不是方法。員工那一次修怎麼查，完全放生。
- **Minor 匯總**：reviewer 的 `## Minor` 寫進 report 之後沒有任何人再讀它。superpowers 是一路帶到
  最後整枝 review 去 triage（明文：「a roll-up nobody reads is a silent discard」）。dkbo 的三個
  載體（`process.md`、整枝評議、`report.md` 的遺留段）都已經存在，只是沒接起來。
- **修復迴圈中間層**：dkbo 是「同一個人再試一次，不過就叫人」。superpowers 是五輪，而且第 4 輪
  換更強的模型重派，理由是「撐過三次 resume 通常表示實作者看不見自己的問題」。
  「同一個人再試一次」與「換一個腦袋試一次」在成本上差很多，dkbo 目前沒有後者。

## 3. 不做什麼

- **不做 superpowers 的五輪迴圈**。dkbo 的哲學是早點打擾人，兩輪（原人一次、換腦袋一次）就升報。
- **不引進 ledger**。`process.md` + `state/` + `dk-resume` 已經是同一件事的更強版本（可執行的看板）。
- **不給員工 skill 觸發機制**。`.dkbo/skills/` 維持領導專用；員工端的方法論用「提示指路 + 獨立方法檔」
  達成同樣的 just-in-time 效果。
- **不改 commit 模型**。員工在波內不 commit、`dk-wave-close` 過閘後統一 commit 一次，這條不動。
- **不新增 `settings.env` 鍵、不新增 skill、不新增 symlink。**

## 4. 波 1 — brief 契約擴充

### 4.1 新增 `## 全域約束` 段

位置：`templates/brief.md` 的「目標」之後、「驗收標準」之前。內容是版本下限、命名與文案規則、
平台要求這類橫切約束，一行一條，**值逐字**。沒有就寫「無」（照現行「共用契約」段的慣例）。

- 新 reader：`lib/brief.sh` 的 `dk_brief_constraints()`，回傳段落內文。
- 流向：`dk-wave-open` 把它算進每一份成員切片（`templates/brief-member.md` 新增
  `## 全域約束（全文）`），`dk-review` 把它算進 reviewer 切片（`templates/brief-reviewer.md`），
  `dk-brief-review` 把它算進計畫審查切片（`templates/brief-reviewer-plan.md`）。

### 4.2 「共用契約」從自由文字升級成表格

不新增獨立的 `## 介面` 段（見裁定 1）。現行段落改成固定欄位的表格：

| 契約 | 擁有者 | 消費者 | 形狀／簽名 | 變更流程 |
|---|---|---|---|---|
| （範例）login API | backend | frontend, qa | `POST /login {user,pw} → {token,exp}` | 動它要先 ESCALATE |

「擁有者」填一個成員短名；「消費者」填一個或多個，逗號分隔。兩欄都用所有權表的成員短名，沒有就填 `—`。
切片本來就帶 `## 共用契約（全文）`，所以形狀自動流到每位員工手上，不必新增切片欄位。

### 4.3 新的機械閘

`dk-brief-check` 新增兩條，並用「段落存不存在」當新舊 brief 的判別器
（0.8.0 的 request.md 空殼 sentinel 用過同一招）：

| 情況 | 判定 |
|---|---|
| `## 全域約束` 段不存在 | WARN（0.9.0 之前建立的 brief） |
| 段落存在但空 | FAIL（新範本產的，沒填）|
| 共用契約段沒有任何 `\|` 開頭的資料列 | WARN（舊的自由文字格式） |
| 有表格但某列的擁有者、或消費者逗號拆開後的任何一個，不在所有權表的成員欄也不是 `—` | FAIL |

最後一條是 superpowers 的 preflight scan 在做的事（「one row for every pair of tasks that share
an interface」）—— 在那側是 controller 手動比對並寫成表格，在 dkbo 是 shell 驗掉，零 token。

## 5. 波 2 — 品質方法論

### 5.1 TDD：report 證據制

`templates/report-employee.md` 的 `## 測試` 段改成兩個小節：

```
## 測試
### 紅
（先寫的那條測試、跑它的指令、失敗輸出）
### 綠
（實作後同一條指令的通過輸出）
```

- `dk-wave-close` 的 gate b 從「`## 測試` 底下有非空非括號行」升級成「`### 紅` 與 `### 綠`
  兩個小節都在，且各自底下有非空內容」。gate b 只掃 `group: dev` 的成員，所以 qa 與 reviewer
  的 report 格式不受影響。
- `lib/prompt.sh` 的首輪提示加上順序：先寫會失敗的測試、跑它確認失敗、再寫最小實作讓它過。
- 出口：純文件波與探測型工作允許 `### 紅` 寫 `不適用: <理由>`（見裁定 2）。

驗得到的理由：員工要偽造一段失敗輸出，比真的先寫測試還貴。

### 5.2 systematic-debugging：新檔 `.dkbo/methods/debugging.md`

約 40 行，內容是方法不是規則：先重現再修、根因追蹤（沿著錯誤往上找到第一個說謊的地方）、
二分法縮範圍、一次只改一件事、修完重跑**原症狀**而不是宣稱好了、改不動就寫下「試過什麼、
排除了什麼」再升報。

- `PROTOCOL.md` 的 BUG 列加一行指路：收到 BUG 先讀 `$DK_ROOT/methods/debugging.md`。
- `[FIXED]` 的規範要求附根因一句；根因與排除過的假設寫進自己的 report。
- `methods/` 是新目錄，自動落在 rsync 升級的覆蓋範圍內（exclude 清單只有 `tasks`、`PROJECT.md`、
  `decisions.md`、`roles/*`、`.sessions`、`settings.env`）。
- 主要載體是 `lib/prompt.sh` 與 `templates/`，**不是 `roles/`** —— 升級對 roles 是
  `--ignore-existing`，既有專案永遠拿不到寫在角色檔裡的修正（0.6.3 已為 qa 的等待規則裁定過一次）。
  角色檔骨架同步補一行，那是給新專案的。

## 6. 波 3 — 審查迴圈

### 6.1 Minor 匯總

接起三個已經存在的載體：

1. 領導讀完 reviewer report 後，把 Minor 逐條收成 `dk-process "minor N: <一行>"`。
2. `dk-review --task`（結案整枝評議）的 reviewer 切片新增 `## 本任務累積的 Minor`，內容是
   `grep ' minor: ' process.md`，請 L 檔 reviewer triage 哪些必須修才能 merge。
   逐波審查時這一段不填（`templates/brief-reviewer.md` 的 `{{MINORS}}` 只在 `--task` 時有值）。
3. 未修的落進 `report.md` 的「未完成／遺留」段。

機械閘只做軟警告：`dk-task-close` 發現 `process.md` 有 `minor:` 行而 `report.md` 沒提到時提醒，
不阻擋（見裁定 4）。

### 6.2 修復迴圈改成兩輪

`PROTOCOL.md` 的「修復迴圈上限一次」改成：

```
BUG → FIXED → 再驗仍失敗
  → 領導換腦袋：dk-spawn <role> <alias> --handoff "<原因>"
  → 再驗仍失敗 → ESCALATE（關卡②）
```

新增 `dk-spawn --handoff "<原因>"`（隱含 `--resume`）：

- 強制帶原因字串，腳本自己補完 ruling 格式寫進 `process.md`，所以「換人那一步一定有 ruling」
  是結構保證，不是事後驗（見裁定 5）。
- 用一份**不同的**首輪提示。現行 `--resume` 說的是「從 state 續作，不要重做已完成的項目」——
  對接手的新腦袋是錯的指示：它要重做，只是不能重走死路。`--handoff` 的提示改成：上一位修過一次
  沒成功，`state` 與 report 裡有它試過什麼、排除了什麼，先讀 `methods/debugging.md` 再動手。
- 換的是 kind（挑未熔斷者）或檔位（`--tier L`），由領導依 `DK_KIND_DOWN` 裁定。

`skills/run/SKILL.md` 的故障段同步這條。

## 7. 裁定紀錄

| # | 裁定 | 原因 | 若錯的代價 |
|---|---|---|---|
| 1 | Interfaces 擴充「共用契約」成表格，不另開 `## 介面` 段 | 員工只讀切片，兩個講同一物件的段落必然不同步 | 治理與形狀擠在一張表，欄位變寬 |
| 2 | 純文件波允許 `### 紅` 寫 `不適用: <理由>` | 沒有出口的話 docs 波永遠關不掉 | 有人拿它當萬用逃生門，靠 reviewer 抓 |
| 3 | `[FIXED]` 的根因不加 `dk-msg` 機械閘 | 措辭比對太脆；員工會卡在遣詞而不是缺陷 | 根因只靠規範要求，可能有人不寫 |
| 4 | Minor 匯總只做軟警告 | 硬擋會讓一條風格意見卡住結案 | 領導可能漏收，靠整枝 reviewer 兜底 |
| 5 | `--handoff` 自動落 ruling，取代事後驗 | 事後驗要認「同一 bug 的第二輪」這種事件序列，是既有閘門沒做過的形狀，容易誤判 | 領導繞過 `--handoff` 手動換人時沒有 ruling |
| 6 | 舊格式 WARN、新任務 FAIL | 進行中的任務升級後不會卡死；新範本帶新段落自然汰換 | 兩種格式並存一段時間 |

## 9. 測試策略

bats-core + `tests/stub` 的假 herdr，零 token，照現有 354 筆的慣例。估 +45 筆
（波 1 約 18、波 2 約 15、波 3 約 12）。否定斷言一律用 `tests/helpers.bash` 的 `refute_grep`，
不要寫 `! grep -q`（0.8.0 的教訓：POSIX 對 `! cmd` 豁免 `set -e`，那種斷言不在最後一行時恆真）。

## 10. 升級影響

- `settings.env` 無新鍵；`install.sh` 無新 symlink；照 README 的 rsync 流程即可。
- `methods/` 是新目錄，在覆蓋範圍內，升級自動取得。
- **既有專案進行中的任務不受影響**：舊 brief 走 WARN 路徑，波照跑（裁定 6）。
- `roles/*.md` 的骨架有更新但升級不覆蓋既有 —— 這一版的行為不依賴角色檔，想同步的人自己 diff。
- CHANGELOG 要寫明：`dk-brief-check` 對 0.9.0 之後新建的 brief 多兩道 FAIL。

## 11. 波次與所有權

**三波都指派同一位成員 `backend`**，審查 `kinds: claude codex`。

理由是改動集互鎖，不是偷懶：`.dkbo/bin/dk-review` 被波 1（全域約束進 reviewer 切片）與波 3
（Minor 清單進整枝評議切片）各要改一次，`.dkbo/lib/prompt.sh` 被波 2（TDD 與除錯指路）與波 3
（`--handoff` 提示）各要改一次，`.dkbo/PROTOCOL.md` 同樣被波 2 與波 3 各要改一次。所有權表是
**跨波的**（一位成員一列），拆成不同成員會被 `dk-brief-check` 判重疊，而拆完也換不到並行 ——
波與波之間本來就是順序的，並行只發生在同一波內，而這個任務的同一波裡沒有可以乾淨切開的兩半。

同一位成員跨三波不等於同一個腦袋跑到底：每一波 `dk-wave-close` 關掉 pane，下一波 `dk-spawn`
重開一個。context 每波重置，正好是 superpowers「fresh subagent per task」的同一件事。
